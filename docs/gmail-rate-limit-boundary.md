# Gmail rate limits: what is actually scoped to what

**Investigated:** 2026-08-27
**Branch:** `feat/gmail-call-logging` @ `2de3e07`
**Scope:** evidence only. No production change was made, no OAuth grant revoked,
no `users.stop` issued, no limiter or sync behaviour altered.

This file exists because the attachment work is about to add a second class of
Gmail traffic, and the previous mental model — *"separate Cloud projects means
separate Gmail limits"* — is **half true in a way that is worse than being
simply wrong.** The half that is true is the half we already fixed. The half
that is false is the half attachments will land on.

Every claim below carries one of:
`CONFIRMED BY GOOGLE API DEFINITION` · `CONFIRMED BY GOOGLE DOCUMENTATION` ·
`CONFIRMED BY TELEMETRY` · `CONFIRMED BY CODE` · `INFERENCE` · `UNKNOWN`.

---

## 0. The one-paragraph answer

Gmail enforces **two independent families of limit**. The quota-unit family is
metered by Google Cloud and is scoped **per user *per project*** — Google's own
Service Usage API literally reports the unit string `1/min/{project}/{user}`, so
separate projects genuinely do get separate quota-unit budgets. The second
family — **concurrency, bandwidth and sending** — is enforced inside Gmail, is
attached to the **mailbox**, and Google states in writing that it is *"shared by
all Gmail API clients accessing a user."* No project split, no OAuth client
split, and no change of project ownership can partition it. Today Mailroid's
traffic is quota-unit-shaped, so the project split we made on 2026-08-26 appears
to have worked. Attachments are bandwidth-shaped and concurrency-shaped, so they
will land squarely on the family the split does not protect.

## 3. The actual rate-limit boundary, dimension by dimension

### 3.1 The two families

`CONFIRMED BY GOOGLE DOCUMENTATION` —
<https://developers.google.com/workspace/gmail/api/guides/handle-errors>,
<https://developers.google.com/workspace/gmail/api/reference/quota>.

> "A 429 'Too many requests' error can occur due to daily per-user limits
> (including mail sending limits), **bandwidth limits**, or a **per-user
> concurrent request limit**."

> "The API has per-user upload and download bandwidth limits that are equal to,
> but independent of, IMAP. **These limits are shared across all Gmail API
> clients for a user.**"

> "The Gmail API enforces a per-user concurrent request limit (in addition to
> the per-user rate limit). **This limit is shared by all Gmail API clients
> accessing a user** and ensures that no API client is overloading a Gmail user
> mailbox or their backend server."

Those two sentences are the load-bearing evidence in this entire document. They
are Google stating, unprompted, that these limits do **not** partition by
client — and an OAuth client is exactly what a project split gives you.

### 3.2 The boundary table

| dimension | independent quota-unit budget? | independent concurrency / bandwidth / sending? | evidence |
|---|---|---|---|
| **Gmail user / mailbox** | it *is* the sub-key of the per-project budget | **it IS the boundary — nothing partitions it** | API definition + docs |
| **Google Cloud project** | **YES** — unit string `1/min/{project}/{user}` | **NO** | Service Usage API |
| **OAuth client** | no independent budget of its own; inherits its project's | **NO** — "shared by all Gmail API clients" | docs |
| **Cloud billing account** | no — quota is per project, not per billing account | **NO** | Service Usage API |
| **Google account owning the project** | no — irrelevant; the project is the key | **NO** | Service Usage API |
| **OAuth grant / authorization** | no | **NO** | docs |
| **API credential (key/SA)** | no | **NO** | docs |
| **Region / location** | no — `location: global` | no | Monitoring resource labels |

### 3.3 Why the project dimension really is independent

`CONFIRMED BY GOOGLE API DEFINITION`. The Service Usage API does not describe
the per-user limit in prose; it emits a machine-readable unit string:

```
unit = 1/min/{project}/{user}
```

`{project}` and `{user}` are both key components of the same bucket. Two
projects hitting one mailbox are two distinct buckets. This is the strongest
form of evidence available for §4 and is not an inference.

### 3.4 Negative evidence: Cloud never saw a quota breach

`CONFIRMED BY TELEMETRY`. Queried for both projects across 24–27 Aug:

| metric | result |
|---|---|
| `serviceruntime.googleapis.com/quota/exceeded` | **400 — metric not available for this service** |
| `serviceruntime.googleapis.com/quota/ratev2/exceeded` | **no data** |
| `serviceruntime.googleapis.com/quota/concurrent/exceeded` | **no data** |
| `serviceruntime.googleapis.com/quota/concurrent/usage` | **no data** |
| `serviceruntime.googleapis.com/quota/concurrent/limit` | **no data** |

Every 429 Mailroid has seen was raised by Gmail itself
(`caribou.api.proto.MailboxService.*`) and **never** by the Cloud quota layer.
That is the empirical form of the §7 distinction: our 429s have not been project
quota refusals at all. They have been Gmail-side per-mailbox throttling.

One honest caveat: `concurrent/*` returning *no data* means "not populated for
Gmail", not "we proved concurrency was never the cause". Gmail does not expose
its concurrency counter through Cloud Monitoring. `UNKNOWN` whether any specific
429 was concurrency-driven; `CONFIRMED` that none was Cloud-quota-driven.

### 3.5 Bandwidth — the limit attachments will meet

`CONFIRMED BY GOOGLE DOCUMENTATION` — per-user, per day, shared with IMAP and
across all clients:

| | limit |
|---|---|
| Download | **2,500 MB/day** (Workspace; the published IMAP figure) |
| Upload | **500 MB/day** |

`UNKNOWN` for free `gmail.com` accounts — Google publishes the table only under
Workspace admin documentation, and Mailroid's test mailboxes are consumer
accounts. Treat 2.5 GB/day as an **upper** bound, not a floor.

**Quota units do not measure bytes.** `messages.attachments.get` costs the same
handful of units whether it returns 4 KB or 24 MB. A limiter that counts units
is structurally blind to bandwidth. This is the single most important sentence
in this document for the attachment work.

## 4. Two projects, one Gmail account

```
Gmail account 009
    ├── Project A → OAuth client A
    └── Project B → OAuth client B
```

**If Project A spends quota units against 009, can Project B still call?**
**YES** — for the quota-unit family. `1/min/{project}/{user}` guarantees B has
its own 15,000/min and 6,000/min budget for mailbox 009. `CONFIRMED BY GOOGLE
API DEFINITION`.

**Will B nonetheless get 429s because of A?**
**YES, under three conditions**, none of which A's project budget protects
against — and one of which we have observed:

1. **Concurrency.** A's in-flight requests and B's count against the *same*
   per-mailbox concurrent-request limit. `CONFIRMED BY GOOGLE DOCUMENTATION`.
2. **Bandwidth.** A's attachment downloads consume 009's shared daily
   download allowance. `CONFIRMED BY GOOGLE DOCUMENTATION`.
3. **Gmail-side per-user throttling that outlives the burst.** Observed
   directly: §2.3, a project at 0.4% of its ceiling receiving
   `User-rate limit exceeded`. `CONFIRMED BY TELEMETRY`.

**Why.** The project is a *billing and metering* key. The mailbox is a
*resource*. Google meters spend per project so one customer cannot bill another;
it protects the mailbox per mailbox so no number of customers can overload one
person's inbox. Those are different jobs, so they use different keys — and only
the first one has "project" in it.

## 5. Four developers, four projects, one mailbox

**Can Developer A's traffic cause B, C and D to get 429s?** **YES.**

Four projects give four independent quota-unit budgets, so A cannot exhaust
B's *units*. But all four share mailbox 009's concurrency slot, its daily
bandwidth, its sending limit, and any Gmail-side penalty A earns. Developer A
running one full mailbox sync — 9,800 `threads.get` at four in flight, as
production did on 26 Aug 05:00 — pushes 009 into exactly the state §2.3
recorded, and B, C and D inherit it.

Worse, and specific to Mailroid: **each developer's `users.watch` call silently
steals the mailbox from the other three** (§9). Four developers on one mailbox
is not merely rate-limit-risky; it is functionally broken.

### The safe development model

**One mailbox belongs to exactly one environment at a time.** Not "one project
per developer" — that is the axis that does not help.

| | |
|---|---|
| Production mailboxes | never connected anywhere but production |
| Each developer | their **own** disposable test mailboxes, connected only to their own environment |
| Shared test mailbox | permitted only if genuinely serialised — one developer at a time, with a `users.stop` handover. Cheaper to create another mailbox. |
| Per-developer Cloud project | still worth having — it isolates units, Pub/Sub topics and webhook endpoints. Just do not mistake it for mailbox isolation. |

## 6. Does project ownership change the boundary?

```
Google account A  → Project A → Gmail 009
Google account 009 → Project B → Gmail 009      (project owned by the mailbox itself)
```

**Does creating the project under `009` rather than
`<developer Google account>` create an independent Gmail rate-limit
boundary?** **NO.**

`CONFIRMED BY GOOGLE API DEFINITION`: the quota key is
`1/min/{project}/{user}`. There is no owner component. Project B under `009`
gets its own budget for exactly the same reason Project B under any other
identity would — because it is a different **project**, not because of who owns
it. Ownership contributes nothing.

And the mailbox-scoped family is unaffected either way: `009` cannot be given a
second concurrency slot or a second daily bandwidth allowance by owning a Cloud
project. A mailbox has one of each, full stop.

`INFERENCE`, and a useful sanity check: if ownership *did* partition the limit,
every rate-limited integration could be trivially uncapped by having the end
user create their own Cloud project — which would make Gmail's mailbox
protection meaningless.

## 7. Project quota vs. mailbox throttling, concretely

```
Project A ── 20,000 units/min ──► Gmail 009 ──► 429
Project B ── 50 units/min     ──► Gmail 009 ──► ???
```

There are two different 429s and they answer differently:

**If A breached its own per-project-per-user unit budget** (>15,000/min
`default`, or >6,000/min `total_query_cost`), the refusal is a *Cloud quota*
refusal, keyed on `{project=A, user=009}`. **B is unaffected.** B has its own
bucket and sails through.

**If A overloaded the mailbox** — too many concurrent requests, too many bytes,
or enough sustained pressure for Gmail to apply a per-user penalty — the refusal
comes from Gmail keyed on `009` alone. **B gets 429s too**, and keeps getting
them until Gmail's window passes, regardless of how idle B is.

Our observed 429s are the second kind (§2.3, §3.4).

So the question *"the projects have different limits, so why were both
environments affected?"* has a precise answer:

> The projects **do** have different limits, and those limits were never the
> ones being hit. The limit that was hit does not have a project in its key.

On 25 August this was moot anyway: both environments were literally the *same*
project (§2.1). The split fixed the unit-budget sharing. It did not, and cannot,
fix the mailbox sharing — and the mailbox sharing is what remains.

## 8. Mailroid's implementation, audited

All `CONFIRMED BY CODE` unless marked.

| area | how it works today |
|---|---|
| OAuth grants | corsair-encrypted tokens in `corsair_accounts`, keyed by tenant, decrypted with `CORSAIR_KEK` |
| Mailbox → tenant | [`gmail_tenant_mappings`](../packages/database/models/gmail-tenant-mappings.ts), **`email_address` is the PRIMARY KEY** — one mailbox maps to one tenant *per database* |
| Environment identification | **none.** There is no `APP_ENV`, no allowlist, no guard. Environments differ only by which `.env` a process loaded |
| Watch registration | [`startGmailWatch`](../packages/services/gmail/watch.ts) → `users.watch` with `GMAIL_PUBSUB_TOPIC` from env |
| Watch renewal | `gmailWatchCron` at 00:00 UTC + `bootstrapGmailWatches` on **every process start**, both at a 48h threshold |
| Watch teardown | **`users.stop` is never called anywhere in the codebase** |
| History cursor | `gmail_tenant_mappings.last_history_id`, advanced only after a fully successful ingest — correctly guarded |
| Sync trigger | `triggerGmailSync` → Inngest `gmail/sync.requested`, or an in-process fallback |
| Retries | `withGmailRetry`, `retries = 4` (5 attempts); 429 deliberately **not** retried — correct, and well reasoned |
| Rate limiting | `quota-limiter.ts`, GCRA per bucket, **keyed on `tenantId`**, in-process, opt-in via `GMAIL_QUOTA_PACING=on` |
| Concurrency | `mapWithConcurrency(4)` in sync; `ingestAllOrThrow(concurrency=2)` in webhook — per call site, not per mailbox |

### 8.1 Confirmed bugs

**B-1 — No environment boundary of any kind.**
[`gmail-oauth.ts:36-46`](../apps/api/src/auth/gmail-oauth.ts#L36-L46) accepts
any mailbox that completes OAuth and immediately calls `storeGmailConnectedEmail`
→ `startGmailWatch` → `triggerGmailSync`. Nothing asks whether this mailbox
belongs to production. A developer connecting a production mailbox locally
steals its watch and starts a full sync against it, and this is precisely what
2026-08-25 was.

**B-2 — `users.stop` is never called.**
Grep across `packages/` and `apps/`: zero call sites. Disconnecting a mailbox,
rolling back a half-finished connect, or deleting a mapping all leave Google's
watch live for up to 7 days.

**B-3 — The limiter's bucket key is `tenantId`, not the mailbox.**
[`quota-limiter.ts:332-336`](../packages/services/gmail/quota-limiter.ts#L332-L336).
Today `email_address` is a primary key so it is 1:1 *within one database* — but
across local and prod the same mailbox is two tenants with two independent
buckets, each pacing to the full rate. Two environments on one mailbox pace at
2× the intended rate and neither can see it.

**B-4 — Attachment retry × recovery multiplication (H-C, now confirmed).**
`stash@{1}:packages/services/attachments/gmail-fetch.ts:131-212` wraps a 3-pass
recovery loop inside `withGmailRetry(retries=4)`, with `refreshedToken` and
`refreshedId` declared **inside** the retried closure, so every outer retry
re-arms both recoveries. Upper bound **≈25 Gmail calls for one logical
attachment fetch**, and every one of them is a *bandwidth* call. Static
inspection is conclusive on the structure; the bound is `INFERENCE`.

### 8.2 Architectural weaknesses

- **W-1** — The limiter is process-global module state. Correct today (one
  container) and documented as such; wrong the moment a second replica, an
  out-of-process worker, or a script runs.
- **W-2** — Concurrency is set per call site (`4` in sync, `2` in webhook), so
  the true in-flight count against one mailbox is the *sum* of whatever happens
  to be running. Nothing enforces a per-mailbox ceiling, which is the dimension
  Gmail actually protects.
- **W-3** — `bootstrapGmailWatches` runs on **every** process start. Under
  `tsx watch` that is a Gmail load generator: `logs/app.log` shows **26**
  `http server is running` lines. Harmless when nothing is due (Gate 2), 100
  units per mailbox when something is.
- **W-4** — Nothing measures bytes anywhere. No byte counter, no bandwidth
  budget, no per-mailbox daily ceiling.

### 8.3 Configuration problems

- **C-1** — `GMAIL_QUOTA_PACING=on` is set in the **local** `.env`. `UNKNOWN`
  whether it is set on the VPS. If it is not, production is entirely unpaced —
  and production is where the 9,800-thread sync ran.
- **C-2** — `INITIAL_SYNC_CONCURRENCY` is unset, defaulting to 1. Fine now;
  a per-mailbox rather than per-process meaning is what it will need later.

### 8.4 Unknowns requiring further testing

## 9. The watch problem

### 9.1 One watch per mailbox

`CONFIRMED BY GOOGLE API DEFINITION` — the Gmail v1 discovery document:

```
users.watch  → params: [userId]         response: WatchResponse
WatchResponse properties: historyId, expiration
users.stop   → params: [userId]         request: (none)   response: (none)
```

`watch` returns **no watch id and no channel id**. `stop` takes **only
`userId`** and no body. There is therefore no way to address a second watch and
no way to stop one of several. **A mailbox has exactly one watch slot, and
calling `watch` again necessarily replaces whatever was there — including its
topic, which is the thing that differs between our environments.**

This is stronger evidence than the prose docs, which (checked) do *not* state
the replacement behaviour at all. The prior belief was correct; it now has a
citation.

| question | answer | evidence |
|---|---|---|
| Multiple active watches per mailbox? | **No — one** | API definition |
| Another project registers a watch for the same mailbox? | Takes it over; pushes go to *its* topic | API definition |
| Previous watch replaced? | **Yes** | API definition |
| Watch lifetime | 7 days; Google recommends renewing daily | documentation |
| Local connection deleted without `users.stop`? | Watch survives at Google; pushes keep arriving | telemetry, below |
| Stale watch pushing to an env with no mapping? | **Yes, observed** | telemetry, below |

### 9.2 Observed, not theorised

`CONFIRMED BY TELEMETRY` — `logs/app.log`:

```
46 × [WEBHOOK] delivery
46 × [WEBHOOK] unresolvable mailbox on gmail push
46 × [WEBHOOK] ignoring gmail push for unmapped mailbox
```

Two distinct mailboxes (digests `0cfe66a5…`, `107f9f96…`) are pushing to the

Mailroid handles this correctly and cheaply: the push is dropped before any

mailboxes receive is going nowhere.** If either is a production mailbox, that is
silent production mail loss right now — which is exactly what U-1 resolves.

## 10. The full-sync chain

### 10.1 Restart is NOT the direct cause

**`CONFIRMED BY CODE` and `CONFIRMED BY TELEMETRY`.** The prior assumption is
**wrong as stated** and should be corrected wherever it is repeated.

A restart runs `bootstrapGmailWatches`, which renews **only** watches that are
missing or inside the 48h threshold — deliberately not a re-register sweep
([watch.ts:114-131](../packages/services/gmail/watch.ts#L114-L131)). Gate 2
proved the idle case: 8m43s, one uninterrupted run, **zero** `history.list`,
zero background polling, one operator-triggered Gmail call. `logs/app.log` shows
26 restarts against a total of ~15 recorded Gmail calls.

Restart amplification is real but **bounded and separate**: 100 units per due
mailbox per boot, and nothing at all when nothing is due.

**The one genuine restart→full-sync path** is narrower than assumed:
[`triggerGmailSync`](../packages/services/gmail/sync-metadata.ts#L439-L467)
falls back to an **in-process, non-resumable** sync when `INNGEST_EVENT_KEY` is
unset. That path restarts from category 0 on every process restart. It is
explicitly documented in the code as non-resumable, and `INNGEST_EVENT_KEY` is
set in local `.env` — so this fallback is **not** what ran. `UNKNOWN` for
production (part of U-2).

### 10.2 The chain that IS real

| link | verdict | evidence |
|---|---|---|
| watch overlap → env loses pushes | **CONFIRMED** | §9.1 API definition + §9.2 46 orphaned pushes |
| missed pushes → cursor goes stale | **CONFIRMED BY CODE** | cursor advances only in `syncHistoryForTenant`; no pushes, no advance |
| stale cursor → `history.list` 404 | **CONFIRMED BY GOOGLE DOCUMENTATION** | history retention window passes `startHistoryId` |
| 404 → automatic full sync | **CONFIRMED BY CODE** | [webhook-sync.ts:259-273](../packages/services/gmail/webhook-sync.ts#L259-L273) — `triggerGmailSync` with no gate, no operator, no notice |
| full sync → thousands of calls | **CONFIRMED BY TELEMETRY** | 26 Aug 05:00Z prod: 98 `threads.list` pages × 100 = 9,800 threads, 9,507 `threads.get`, 95,070 units in one hour |
| → 429 | **partially** | that hour recorded 1 `4xx`; the 429s came later and elsewhere. The full sync is the *load*, not always the *refusal* |

**Checkpointing works.** `gmailInitialSync` wraps every page in its own
`step.run`, so a crash resumes at the exact page, and hands off to a fresh run
every 15 pages. `CONFIRMED BY CODE`, and corroborated: local's two completed
syncs (1,643 and 561 messages) both reached `complete` with a `null` cursor.

**But the fallback always starts from page 1.** `triggerGmailSync(userId)` sends
no `categoryIndex` and no `pageToken`, so a 404-driven resync re-walks all nine
categories from the beginning. And
[`syncCategoryPage`](../packages/services/gmail/sync-metadata.ts#L320-L390)
issues `threads.get` for **every** thread on every page with **no check for
threads already stored** — dedup happens in `processMessages`, *after* the
network call. A resync of a known mailbox therefore costs the same as a first
sync. `CONFIRMED BY CODE`.

**Concurrent syncs can multiply this.** `gmailInitialSync` caps at
`INITIAL_SYNC_CONCURRENCY` (default 1) *per Inngest app*, which is per
environment. Two environments on one mailbox is 2×, and nothing anywhere knows.

## 11. The limiter vs. the real boundary

### 11.1 Scope

**The premise in the brief is out of date.** The limiter is **not** process-wide
at 75 units/sec. It is a GCRA bucket **per `tenantId`**
([quota-limiter.ts:332-336](../packages/services/gmail/quota-limiter.ts#L332-L336)),
each paced independently at 75 units/sec with a 250-unit burst, held in
process-global module state.

And it demonstrably works. Live measurement, run `08435b61450b`:

```
threads.get  calls=190  quotaUnits=7600  windowMs=106860
             waitedTotalMs=296316  waitedMaxMs=1819  errors=0
```

7,600 units over 106.9s = **71.1 units/sec** against a 75 target, with 296s of
deliberate wait across 190 calls. `CONFIRMED BY TELEMETRY`.

```
Mailroid protects:  75 quota units/sec, per tenantId, per process, opt-in

Gmail protects:     15,000 units/min/{project}/{user}   (= 250/sec)
                     6,000 units/min/{project}/{user}   (total_query_cost, = 100/sec)
                     per-mailbox concurrency   — shared across ALL projects
                     per-mailbox bandwidth     — shared across ALL projects
                     per-mailbox sending       — shared across ALL projects

Therefore:          the limiter guards the ONE dimension that was already
                    isolated by the project split, and guards NONE of the
                    three that are not.
```

The three mismatches, in order of consequence:

1. **Wrong key.** `tenantId`, not mailbox. Two environments = two buckets = 2×
   the rate, invisibly. (B-3)
2. **Wrong quantity.** Units, not bytes and not in-flight count. Structurally
   cannot see the limits attachments will hit. (W-4)
3. **Wrong scope.** One process. (W-1)

### 11.2 A measured discrepancy, not hidden

Reconciling the ledger against the Cloud meter for the same window exposes a
disagreement that §16 requires be recorded rather than smoothed over.

| method | published table / ledger price | measured in `gmail.googleapis.com/default` | agree? |
|---|---|---|---|
| `users.watch` | 100 | 100 | ✅ |
| `threads.list` | 10 | 10 | ✅ |
| `drafts.list` | 5 | 5 | ✅ |
| `history.list` | 2 | 2 | ✅ |
| `getProfile` | 1 | 1 | ✅ |
| `labels.get` | 1 | 1 | ✅ |
| **`threads.get`** | **40** | **~10** | ❌ 4× |
| **`messages.get`** | **20** | **~5** | ❌ 4× |
| **`drafts.get`** | **20** | **~5** | ❌ 4× |

Derivation for `threads.get`, the cleanest case — 26 Aug 05:00Z, production:
`threads.list` spent 980 units = 98 pages at `maxResults: 100` = 9,800 threads;
`threads.get` spent 95,070 units for those threads; 95,070 ÷ 9,800 = **9.7**.
The hour's request count (9,784) independently corroborates ~9,800 calls.

Every method that agrees is a *list* or a *counter*; every method that disagrees
by exactly 4× is a *fetch one resource*. `INFERENCE`: the meter prices fetches
by response size or `format`, and the published single number is a ceiling —
Mailroid's sync uses `format: "metadata"`, the cheapest form.

Consequences, kept separate:

- **Safe.** The limiter over-charges by 4× on the hot path, so it paces
  ~4× more conservatively than needed. It cannot cause a 429 this way.
- **Costly.** A full sync takes ~4× longer than the budget requires.
- **Do not "fix" this by dividing by 4.** `total_query_cost` — the meter with
  the *tighter* 6,000/min limit — appears to charge roughly 8× the `default`
  meter for `messages.get`, so the binding constraint may be the other way
  round. `UNKNOWN` until U-3 is settled by controlled test.

## 12. Attachments: why this breaks

### 12.1 The methods and what they cost

| operation | published units | measured (`default`) | **bytes** |
|---|---|---|---|
| `messages.attachments.get` | 20 | ~5 (`INFERENCE`, by the §11.2 pattern) | **the whole attachment** |
| `messages.get` (`format: "full"`, to re-resolve a rotated id) | 20 | ~5 | full MIME |
| `messages.send` / `drafts.send` with attachments | 100 | 100 | **the whole upload** |

Two of those three are bandwidth operations, and quota units say nothing about
bandwidth (§3.5).

### 12.2 Amplification paths, all confirmed by code

- **Retry × recovery (B-4).** ≈25 Gmail calls per logical fetch, each a full
  byte transfer, from `stash@{1}` `gmail-fetch.ts:131-212`.
- **Auto-loading thumbnails.** `attachment-list.tsx:104-125` issues
  `<img src="/api/attachments/{id}">` for every image ≤512 KB **with no click**.
  Nothing resizes anywhere: a thumbnail is a **full download**. The route is
  `force-dynamic` with **no `Cache-Control`** (`route.ts:35`), so every mount
  may re-issue; dev StrictMode double-mounts.
- **Single-flight does not help.** `single-flight.ts:24-37` coalesces only
  *overlapping* fetches and deletes the key on settle — sequential remounts,
  which is exactly what thumbnails produce, coalesce nothing.
- **Cold cache is unbounded.** *A cache is not a rate limit.* It bounds steady
  state; it does not prevent the request, and every path where it is never
  populated re-hits Gmail forever.
- **Interactive priority.** `quota-limiter.ts:159-165` classes `thumbnail` and
  `attachment-download` as **interactive** — larger tolerance, allowed to jump
  background reservations. A thumbnail storm gets *priority*.

### 12.3 The arithmetic

One 40-thread inbox screen, three 400 KB images per thread, cold cache:

```
120 downloads × 400 KB          =    48 MB   one screen, one scroll
× 25 (B-4 worst case)           = 1,200 MB   one screen, retry storm
                                             ≈ half a mailbox's DAILY allowance
```

Quota units for those 120 downloads: ~600 of a 15,000/min budget — **4%.** The
limiter would wave every one of them through while consuming 48 MB–1.2 GB of a
shared, cross-project, daily allowance it cannot see.

**And the 25 Aug telemetry says this is not hypothetical.** 13,515 units of
`messages.attachments.get` were spent across two hours — between **339 and
1,356 real attachment fetches**, depending on the §11.2 divisor.

### 12.4 A correction to `AUDIT.md`

`notes/incidents/2026-08-25-gmail-quota/AUDIT.md` records **"attachment fetches
(`last_accessed_at`) = 2"** and concludes the attachment branch is *"close to
exonerated for this window."*

**The Cloud meter contradicts that.** `messages.attachments.get` spent 6,780
units in the 05:00Z hour and 6,735 in the 06:00Z hour — hundreds to thousands of
real fetches. `last_accessed_at` counted **cache rows**, not **Gmail calls**;
fetches that failed, were evicted, raced, or never persisted a manifest row left
no trace in it. The audit measured the wrong side of the cache and drew a
conclusion from a number that could not have shown the traffic.

The audit's own rule caught this and was not applied to its own headline:

> *"Absence of instrumentation is not absence of traffic."*

Attachments are **not** exonerated for 25 August. They were not the *majority*
of the burst — `messages.get` was, at ~95% — but they were present in volume,
and the branch is now the leading candidate for the *next* incident rather than
a cleared suspect. This does not change the incident's root cause (§2.1: one
project, local traffic on production mailboxes); it changes what we may assume
when the branch is unparked.

## 13. Proposed changes

Ordered by evidence strength. Nothing here has been implemented.

### P-1 · Hard environment boundary on mailbox connect

- **Problem** — B-1. Any mailbox can be connected in any environment; doing so
  steals its watch and starts a full sync.
- **Evidence** — §2.1 (the 25 Aug incident *is* this bug); §9.2 (46 orphaned
  pushes right now); `gmail-oauth.ts:36-46` has no guard.
- **Change** — a required `MAILROID_ENV` plus a `mailbox_environment` claim
  checked in the OAuth callback **before** `storeGmailConnectedEmail`. Refuse
  with a plain message naming the owning environment. Start as an env-var
  allow/deny list; a table later if it earns one.
- **Mechanism** — moves the check to the only moment a mailbox can enter an
  environment. Everything downstream — watch, sync, webhook — inherits it.
- **Risk** — a misconfigured list locks a legitimate connect out. Mitigate with
  an explicit, logged override and a clear error.
- **Verification** — attempt to connect a prod mailbox locally: refused, with
  **zero** Gmail calls in `mailroid-local`'s meter for that mailbox.

### P-2 · Watch ownership and lifecycle

- **Problem** — B-2 + §9.1. One watch slot per mailbox; we never release it.
- **Evidence** — discovery doc (`stop` takes only `userId`); 46 orphaned pushes
  spanning 14+ hours.
- **Change** — (a) best-effort `users.stop` on disconnect and on
  `rollbackGmailConnection` *when a credential still works*, silence otherwise;
  (b) record `watch_topic` and `watch_owner_env` on the mapping so a takeover is
  **detectable**; (c) log loudly when a push arrives for an unmapped mailbox —
  it is currently a `warn` that scrolls past.
- **Mechanism** — `stop` releases the slot; the recorded topic makes "someone
  else took this mailbox" a query instead of an archaeology exercise.
- **Risk** — `stop` costs 50 units and issuing it during a quota incident is
  the behaviour the cooldown exists to prevent. Gate it on a healthy mailbox;
  never on a 429 path.
- **Verification** — disconnect locally, confirm pushes stop within minutes.

### P-3 · Never full-sync silently

- **Problem** — a `history.list` 404 fires an unbounded full sync with no
  operator and no notice.
- **Evidence** — [webhook-sync.ts:259-273](../packages/services/gmail/webhook-sync.ts#L259-L273);
  26 Aug 05:00Z, 9,507 `threads.get` in one hour.
- **Change** — on 404, write a `resync_required` flag and **surface it**. Auto
  full sync only under an explicit budget; otherwise wait for a human.
- **Mechanism** — this is CLAUDE.md's *no silent fallbacks on drift*, applied to
  the most expensive fallback in the system.
- **Risk** — a mailbox sits stale until someone acts. Correct: staleness is
  visible and cheap, a surprise 9,800-thread sync is neither.
- **Verification** — force a stale cursor on a test mailbox; expect a flag and
  zero `threads.get`.

### P-4 · Skip what we already have during resync

- **Problem** — `syncCategoryPage` fetches every thread on every page with no
  check for threads already stored (§10.2).
- **Evidence** — code; `processMessages` dedupes only *after* the network call.
- **Change** — filter each `threads.list` page against stored ids before
  expanding, unless an explicit `force` is passed.
- **Mechanism** — `threads.list` returns ids for free. A resync of a known
  mailbox becomes proportional to what changed.
- **Risk** — a locally-stored-but-stale thread is skipped. Bound it by
  comparing `historyId`, and keep `force` for a true rebuild.
- **Verification** — resync a fully-synced mailbox; `threads.get` count should
  fall by ≥90% versus today's baseline of ~1 per thread.

### P-5 · Re-key the limiter to the mailbox, and add a byte budget

- **Problem** — B-3 (wrong key) and W-4 (wrong quantity).
- **Evidence** — §3.1 Google's "shared by all Gmail API clients for a user";
  §11.1 the key is `tenantId`; §12.3 the arithmetic.
- **Change** — (a) key buckets on the **mailbox address**, not `tenantId`;
  (b) add a **per-mailbox in-flight semaphore**, sized well under Gmail's
  concurrency limit and shared across *all* call sites, not per call site;
  (c) add a **per-mailbox daily byte budget** charged by actual response size,
  with attachment traffic refused — not queued — when exhausted.
- **Mechanism** — makes the limiter's key match Gmail's key. (b) and (c) are the
  only controls that touch the two limits a project split cannot partition.
- **Risk** — a byte budget can block a legitimate download. Surface it as a
  clear "daily attachment limit reached", never a silent failure.
- **Verification** — drive a synthetic attachment load; confirm bytes are
  counted, the budget binds, and in-flight never exceeds the semaphore.
- **Note** — do **not** also retune the 75 units/sec figure here. U-3 first.

### P-6 · Fix the attachment retry multiplication

- **Problem** — B-4, ≈25 calls per logical fetch.
- **Evidence** — `stash@{1}` `gmail-fetch.ts:131-212`, flags inside the closure.
- **Change** — hoist `refreshedToken` / `refreshedId` outside the retried
  closure, or narrow what `withGmailRetry` wraps to the single request.
- **Mechanism** — makes recoveries once-per-logical-operation instead of
  once-per-retry, collapsing 5×3 to 3.
- **Risk** — a genuine mid-retry token expiry is no longer recovered. Acceptable:
  the next user action recovers it.
- **Verification** — a test forcing 401-then-404-then-500; assert
  `network_attempts ≤ 5`.

### P-7 · Thumbnails must not be free full downloads

- **Problem** — auto-loading thumbnails are full downloads with no cache header.
- **Evidence** — `attachment-list.tsx:104-125`; `route.ts:35`.
- **Change** — load thumbnails on intent (click / viewport), set
  `Cache-Control: private, max-age=…`, and reclassify `thumbnail` as
  **background** in `INTERACTIVE_TRIGGERS` so it stops jumping the queue.
- **Mechanism** — removes the multiplier before the byte budget has to absorb it.
- **Risk** — a slightly less magical inbox. Worth it.
- **Verification** — mount an inbox screen cold; assert zero
  `attachments.get` until intent.

### P-8 · Confirm production configuration

- **Problem** — U-2: `GMAIL_QUOTA_PACING` may be off in production.
- **Change** — none in code. Read the VPS env and record it here.
- **Verification** — `[GMAIL_PACING] configured` on the container's boot line
  should read `enabled: true`.

### Evaluated and rejected for now

- **Per-developer Cloud projects as a mailbox-isolation strategy.** They isolate
  units, topics and endpoints — all worth having — but §5 shows they do nothing
  for the boundary that matters. Keep them; stop describing them as isolation.
- **Retuning 75 units/sec.** Blocked on U-3 (§11.2). The safe error is the one
  we already have.
- **Moving the limiter to Redis.** Correct eventually (W-1), unnecessary while
  one container runs, and it does not address the mailbox-shared limits.

## 14. Target architecture

### Ownership — one mailbox, one environment

```
                        Gmail mailboxes
                              │
              ┌───────────────┴───────────────┐
              │                               │
           LOCAL                            PROD
     local-only mailboxes            prod-only mailboxes
     (per developer, disposable)     (never connected elsewhere)
              │                               │
     mailroid-local OAuth client      mailroid-499113 OAuth client
     mailroid-local project           mailroid-499113 project
     mailroid-local-webhooks topic    mailroid-webhooks topic
     ngrok endpoint                   https://mailroid.in/api/webhook
              │                               │
     ONE watch slot per mailbox — owned by exactly one side, ever
```

The bottom line is the invariant. Everything above it we already have; that line
is what P-1 and P-2 add.

### Enforcement — where each control sits

```
  mailbox connect (OAuth callback)
         │
         ├─ P-1  is this mailbox allowed in THIS environment?
         │        NO → refuse, zero Gmail calls, name the owner
         ▼ YES
  ┌─────────────────────────────────────────────────────────┐
  │  Gmail API request                                      │
  │      ↓                                                  │
  │  cooldown / pause gate      refuse instantly, free      │
  │      ↓                                                  │
  │  MAILBOX quota bucket       units/sec   ── P-5a         │
  │      ↓                                                  │
  │  MAILBOX in-flight semaphore  concurrency ── P-5b  ◄─── the limit
  │      ↓                                    a project split
  │  MAILBOX daily byte budget    bandwidth  ── P-5c  ◄───  cannot partition
  │      ↓                                                  │
  │  Gmail  ── charge ACTUAL response bytes back to budget   │
  └─────────────────────────────────────────────────────────┘
```

Every control is keyed on the **mailbox**, because that is what Gmail is keyed
on. The project split stays — it is genuinely load-bearing for units, and it is
what keeps a local mistake off production's meter — it is simply no longer
mistaken for the whole answer.

## 15. The eight questions, answered

### Q1 — Different projects and OAuth clients, same Gmail account: can the account's rate limit affect both?

**YES.**

The *quota-unit* budget is genuinely separate: Google's Service Usage API
reports `unit = 1/min/{project}/{user}`, and both our projects show independent
15,000/min and 6,000/min limits. But concurrency, bandwidth and sending are
enforced per **mailbox** and Google states they are *"shared by all Gmail API
clients accessing a user."*

Observed directly: at `2026-08-26T19:00:50Z` the `mailroid-local` project — with
zero successful calls that hour and its last burst two hours earlier at 0.4% of
its ceiling — received `User-rate limit exceeded. Retry after
2026-08-26T19:15:50.717Z`. Cloud Monitoring recorded **no** quota-exceeded event
for either project across the whole period. The throttle was on the mailbox.

### Q2 — Four developers, four projects, one mailbox: can one cause 429s for the others?

**YES.**

Four separate unit budgets, but one shared concurrency slot, one shared daily
bandwidth allowance, one shared sending limit, and one shared Gmail-side penalty
state. One developer's full sync — 9,800 threads, as production ran on 26 Aug —
is enough. On top of which each `users.watch` call steals the mailbox from the
other three (Q7). Mailroid **cannot** safely support multiple development
projects on one mailbox; see §5 for the model that does work.

### Q3 — A project created under Gmail account `009` instead of the developer's: independent boundary?

**NO.**

The quota key is `1/min/{project}/{user}`. There is no owner component. Project B
gets its own unit budget because it is a different *project*, not because of who
owns it — and the mailbox-scoped limits are untouched either way. A mailbox has
one concurrency slot and one daily bandwidth allowance no matter how many Cloud
projects it owns.

### Q4 — Are Cloud project quotas and Gmail-account throttling the same thing?

**NO.** They are different mechanisms, different keys, different enforcers.

Cloud project quota is metered by `serviceruntime`, keyed
`{project, user}`, visible in the console, adjustable by request, and it refuses
with a Cloud quota error. Gmail account throttling is enforced inside Gmail
(`caribou.api.proto.MailboxService`), keyed on the **mailbox alone**, invisible
in Cloud Monitoring, not adjustable, and it refuses with
`User-rate limit exceeded` plus an absolute retry instant — a window that moves
*further out* on every request made inside it.

Every 429 in our evidence is the second kind. `quota/exceeded` is not even
available as a metric for Gmail, and `quota/ratev2/exceeded` has no data.

### Q5 — Does restarting Mailroid directly cause a full mailbox sync?

**NO.**

`bootstrapGmailWatches` renews only watches that are missing or within 48h of
expiry — it is deliberately not a re-register sweep. Gate 2 measured an idle
server for 8m43s: zero `history.list`, zero background polling, one
operator-triggered call. `logs/app.log` holds 26 restarts against ~15 Gmail
calls total.

The one real restart→full-sync path is the **in-process fallback** in
`triggerGmailSync`, taken only when `INNGEST_EVENT_KEY` is unset; that path is
non-resumable and restarts from category 0. `INNGEST_EVENT_KEY` is set locally,
so it was not what ran. Restart amplification is real but bounded: 100 units per
due mailbox per boot.

### Q6 — What actually causes the full mailbox sync?

**A lost Gmail watch, which starves the history cursor until Gmail can no longer
serve the diff.**

```
another environment calls users.watch on the same mailbox   ← the one watch slot
        ↓                                                      is taken over
this environment stops receiving pushes                     ← silently
        ↓
last_history_id never advances (it advances only on a successful ingest)
        ↓
the cursor falls outside Gmail's history retention window
        ↓
history.list returns 404
        ↓
webhook-sync.ts:267 calls triggerGmailSync() — no gate, no operator, no notice
        ↓
full sync from category 0, page 1, re-fetching every thread it already has
        ↓
9,800 threads.get in one hour   (measured, prod, 2026-08-26 05:00Z)
```

The trigger is a **watch takeover**, not a restart. On 25 August the takeover was
trivially available because local and production were the same project pointed at
the same mailboxes.

### Q7 — Can local and production interfere with each other's Gmail watches?

**YES — and one of them is doing it right now.**

Gmail's discovery document is decisive: `users.watch` returns only `historyId`
and `expiration` — **no watch id** — and `users.stop` takes **only `userId`**
with no body. There is no way to address a second watch or to stop one of
several. One mailbox, one watch slot; calling `watch` again replaces it,
including its Pub/Sub topic.

Mailroid calls `startGmailWatch` on every OAuth connect and on every process
start for anything due, and **never calls `users.stop` anywhere**. Right now
`logs/app.log` shows two mailboxes (digests `0cfe66a5…`, `107f9f96…`) pushing to
the local ngrok endpoint with no local mapping, across 14+ hours — 46
deliveries, all correctly dropped, all going nowhere. Whichever environment
previously owned those mailboxes is receiving nothing.

Whether either is a **production** mailbox is **U-1** — unresolved, and it needs
the prod DB tunnel you run yourself (§8.4).

### Q8 — What is the correct architecture?

**Make the mailbox the unit of ownership and the key of every control, and stop
treating the Cloud project as an isolation boundary it was never designed to be.**

1. **One mailbox, one environment, enforced at connect** (P-1). This is the only
   control that prevents the 25 August failure from recurring, and the only one
   that makes multi-developer work safe.
2. **Own the watch slot deliberately** — record the topic and owner, call
   `users.stop` on release (P-2). One slot, so treat it as a lock.
3. **Never full-sync silently** (P-3), and **skip what we already have** when a
   resync is genuinely needed (P-4). Together these turn the worst case from
   9,800 threads into a bounded, visible, operator-acknowledged event.
4. **Re-key the limiter to the mailbox, and give it the two dimensions it does
   not have** — an in-flight semaphore and a daily byte budget (P-5). Units are
   the dimension the project split already protects; concurrency and bandwidth
   are the ones nothing protects.
5. **Fix the attachment amplifiers before unparking the branch** (P-6, P-7).
6. **Keep the per-environment projects**, and keep per-developer ones. They are
   real and useful for units, topics and endpoints. They are just not mailbox
   isolation, and describing them as such is what produced this investigation.

The ordering matters: P-1 and P-2 are the ones that make the current state safe.
P-5 through P-7 are the ones that make attachments safe. Doing the second set
without the first fixes the wrong incident.
